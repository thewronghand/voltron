# 0장 대조군 — 리뷰 7회를 거친 이유

- 날짜: 2026-10-12 ~ 2026-10-14
- 관련: 코드 레포 `docs/chapters/00-baseline.md` (공개 회고 PDR-000), `baseline/button.pl`, `golden/`

## 결정

0장 대조군은 **독립 리뷰가 PASS를 낸 뒤에도** 남은 MEDIUM까지 고치고, 그 수정분만 좁혀 한 번 더 리뷰한 다음 동결했다. 총 7회(FAIL 4 → PASS 3).

## 왜 그렇게까지 했나

대조군은 동결된다(P-4). 이후 모든 챕터가 이 숫자와 이 "누름" 정의를 다른 언어로 재현해야 하므로, 동결 뒤에 결함이 나오면 **전 챕터 재측정**이 된다. 일반 작업이라면 PASS에서 멈췄을 MEDIUM(빌드 동시 실행 충돌, 헤더 미완결 요청 집계)도 동결 전에 처리하는 게 싸다고 판단했다.

## 배운 것

### 1. 로그 형식이 곧 API다

버튼 카운터는 접근 로그를 정규식으로 센다. 그래서 로그 한 줄의 모양이 "누름"의 정의가 된다. 로그를 건드린 두 번의 수정(요청줄 200바이트 자르기, 로그용 2,048자 자르기)이 카운터 코드는 한 줄도 안 바꿨는데 집계 결과를 조용히 바꿨다. `verify`는 수치만 지키므로 둘 다 못 잡았다. 두 번째는 리뷰가 아니라 **긴 쿼리로 실측하다** 잡혔다.

→ 이후 챕터 체크리스트: 로그·이벤트 형식을 바꾸는 변경은 카운터 집계 실측(정상·긴 요청·비정상 요청 각각 몇 건 → 몇 건 집계)을 같이 돌린다.

### 2. 회귀는 수정에서 나온다

결함 3건이 이전 결함을 고친 코드에서 나왔다(공백 경로 `glob`, 파싱 전 자르기, 로그 자르기). 전부 메인(나)이 직접 고친 부분이다. 수정이 작고 국소적으로 맞아 보여도, **수정분과 카운터·verify의 상호작용**을 따로 보지 않으면 놓친다. 7회차에서 범위를 수정분으로 좁히고 "회귀만 보라"고 지시하자 수렴했다.

→ 리뷰 지시에 "이번 수정이 기존 계약(집계 규칙, golden)을 바꾸는지"를 명시 항목으로 넣는다.

### 3. 리뷰어마다 다른 층을 판다

7명 모두 수치는 독립 재계산으로 일치를 확인했고 결함은 하나도 못 찾았다. 결함은 전부 그 바깥에서 나왔다: CLI → 파일시스템 대소문자 → 소켓 전달 → 경로 공백 → 동시성 → 파싱 경계. 새 리뷰어(이력 없음)를 쓰는 규칙이 같은 층만 반복해서 보는 걸 막아 줬다.

### 4. 시간 측정은 경합부터 센다

첫 시간 측정은 부하 평균 약 40(다른 세션의 node 4개)에서 이뤄져 버렸다. 버리고 다음 날 재측정했다(콜드 0.48초, 웜 0.24초, p50 0.33ms). 대조군 시간이 부풀려지면 이후 챕터가 실제보다 좋아 보이므로, **측정 전 `ps`로 최대 CPU 점유 프로세스를 확인**하고 README 각주에 조건을 적는다.
