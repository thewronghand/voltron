# shipping-a-button 기획

> 개발 유머 영상 "Shipping a button in 2026…"에 나온 훈수를 **전부 수용**해서 대시보드 하나를 만들어 보는 실험.
> 결과물은 대시보드가 아니라 **"복잡도에는 이만큼 비용이 든다"는 측정표와 챕터별 기록**이다.

- 작성: 2026-10-12
- 영상: https://www.youtube.com/watch?v=xE9W9Ghe4Jk
- 영상 해설: Synapse `261012 Shipping a button in 2026 영상 해설`

## 1. 가설

훈수를 하나씩 들으면 전부 과해 보인다. 그런데 **전부** 받아들이면 과한 선택들이 서로의 근거가 된다.

```
Rust + Java + TS 서비스 → 다언어 모노레포 → Bazel이 정당해짐
서비스 여러 개 → 서비스 간 통신 → Kafka가 정당해짐
요청이 서비스를 넘나듦 → 분산 트레이싱이 정당해짐
서비스 간 인증 → mTLS·Istio가 정당해짐
```

이 연쇄가 실제로 일어나는지, 일어난다면 **어느 지점에서 무엇이 무엇을 강제하는지**를 기록하는 게 이 프로젝트의 목적이다.

## 3. 절충 규칙

**기본값은 전부 그대로 수용한다.** 절충은 아래 두 경우에만 한다.

1. **문자 그대로 동시에 만족할 수 없을 때**
2. **돈이나 외부 계정이 필요할 때**

범위를 줄이고 싶은 충동(KISS 본능)은 절충 사유가 아니다. 그건 이 실험이 측정하려는 대상이다.

### ① 충돌의 해석 — 대부분 수용으로 풀린다

F1이 마이크로서비스를 요구했으므로, 언어·런타임이 다투는 자리는 **서비스를 나눠 각자 하나씩** 갖게 한다.

| 충돌 | 해석 |
|---|---|
| Rust vs Java vs TS | 서비스를 나눠 셋 다 쓴다 |
| Node vs Bun vs Workers | F2가 셋 다 말했으므로 셋 다 쓴다 |
| Neo4j vs Dgraph | F1이 둘 다 말했으므로 둘 다 쓴다 |
| Leptos vs Dioxus Native | 실행 위치가 달라 다투지 않는다. **웹 포털은 Leptos, 같은 대시보드의 데스크톱 클라이언트는 Dioxus Native.** 둘 다 쓴다 |
| Perl "no containers, no YAML" vs Docker·`app.yaml`·k8s | Perl 배치만 **컨테이너 밖 호스트 cron**으로 돌린다. YAML 없이 동작해야 한다 |
| `random-auth-package` vs CVE 정책 vs SAML | 패키지를 설치하되 **CVE 감사 게이트**를 통과해야 하고, 그 위에 SAML을 얹는다 |

### ② 유료·외부 계정 대체

| 원래 | 대체 | 비고 |
|---|---|---|
| PagerDuty | 무료 알림 채널(웹훅) | 알림 규칙 자체는 그대로 구현 |
| Okta 등 상용 IdP | 로컬 Keycloak | SAML IdP 역할 |
| Cloudflare Workers 배포 | 로컬 `wrangler dev`(workerd) | 런타임 자체는 같음. 배포는 선택 |
| 상용 APM | Jaeger·Prometheus·Grafana 등 오픈소스 | OTel로 수집 |

## 4. 도메인과 데이터

### 가상 회사: Acme Payments

가상의 PG사. **가맹점이 접속하는 클라이언트 포털**의 정산 리포트 대시보드를 만든다.

- **공개 레포**이므로 데이터는 전부 **시드 고정 생성기**로 만든 가상 데이터만 쓴다. 실제 회사명·가맹점명·사내 정책은 넣지 않는다.
- 시드가 고정되어 있으므로 어디서 돌려도 같은 데이터가 나온다(F5 결정적 빌드와도 맞음).

### 데이터 모델 (초안)

```
총판 (distributor)
 └─ 대리점 (agency)
     └─ 가맹점 (merchant)   ← 테넌트. 포털 로그인 단위
         └─ 거래 (transaction)   금액, 결제수단, 승인/취소, 일시
             └─ 수수료 (fee)       요율(bp), 수수료액
         └─ 정산 (settlement)    정산일, 거래 합계, 수수료 합계, 정산액
```

- 금액은 원 단위 정수, 요율은 **basis point 정수**.
- 계층(총판–대리점–가맹점)이 그래프 DB의 실제 쓰임새가 된다.

### 화면 — 모든 챕터에서 고정

측정이 공정하려면 **기능은 처음부터 끝까지 같아야 한다.** 챕터마다 바뀌는 건 아키텍처뿐이다.

| 요소 | 내용 |
|---|---|
| 정산 요약 | 선택 기간의 거래 합계·수수료 합계·정산 예정액 |
| 일자별 표 | 일자별 거래 건수·금액·수수료·정산액 |
| **다운로드 버튼** | **정산 내역서 CSV 다운로드.** 이 프로젝트의 "그 버튼" |
| 버튼 카운터 패널 | 다운로드 버튼이 지금까지 몇 번 눌렸나. 버튼을 위해 쌓은 인프라가 버튼 자신을 센다 |
| API 엔드포인트 | 위 데이터를 내려주는 엔드포인트와 CSV 엔드포인트 |

**완료 조건(모든 챕터 공통)**: 위 다섯 가지가 동작하고, 대조군과 **같은 시드에서 같은 숫자**가 나온다. 5장 이후 데스크톱 클라이언트도 같은 조건을 만족해야 한다.
