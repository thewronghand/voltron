# oracule 백엔드 재구축 기획서 — Spring Boot + Kotlin

> **작성일**: 2026-06-22
> **상태**: 의사결정 확정 (서버리스/tRPC 폐기 → Kotlin 단일 백엔드 신규 구축)
> **목표**: 앱인토스(토스 미니앱)에 출시할 타로/운세 제품 oracule의 백엔드를 Spring Boot + Kotlin으로 **새 프로젝트로** 구축한다.
> **레벨**: 의사결정 + 아키텍처 + 마이그레이션 범위 + 로드맵 (상세 API/스키마 설계는 별도 문서)

---

## 1. 배경 & 문제 정의

oracule은 **앱인토스에 실제로 굴릴 제품**이다. 학습용 토이가 아니라, 회원가입·로그인·결제·환불이 모두 필요한 "돈이 오가는" 서비스다.

### 기존 자산 진단 (`~/dev/tarot/oracule`, t3-turbo 모노레포)

t3-turbo 기반으로 expo(앱)·nextjs(웹)·toss(앱인토스) 3개 앱 + tRPC 백엔드가 이미 있다. 실사 결과:

| 영역 | 상태 | 판정 |
|------|------|------|
| 타로 리딩 (생성/조회/공유/삭제) | tRPC `reading` 라우터 + Gemini + DB 저장 | ✅ 동작 |
| 일일 운세 (유저당 하루 1개) | tRPC `fortune` 라우터 + Gemini | ✅ 동작 |
| LLM 해석 | `gemini` 패키지 (프롬프트 분리, prompts 디렉토리) | ✅ **핵심 자산** |
| 타로 도메인 데이터 | 78장 덱·스프레드·캐릭터(rpPrompt) | ✅ **핵심 자산** |
| DB | Drizzle + Supabase Postgres, 3개 테이블 | ⚠️ 결제 그릇 없음 |
| 로그인 | better-auth(Discord OAuth) + 토스 전용 `tossLogin`(JWT 직접 발급) **이중 구조** | ⚠️ 어정쩡 / Discord는 사실상 죽은 코드 |
| 결제 / 환불 | **전무** | ❌ 없음 |
| 유저 모델 | `email` + `tossUserId`만, 잔액/재화/구독 필드 없음 | ❌ 결제 받을 그릇 없음 |

### 핵심 판단

- **잘 된 것**: 타로 도메인 로직 + Gemini 프롬프트. 이건 **언어 무관한 데이터·프롬프트**라 Kotlin 이식이 쉽다.
- **어정쩡/없는 것**: 인증(이중 구조), 결제·환불(0). 제품의 돈 관련 핵심이 통째로 비어 있다.
- **결론**: "버릴 게 적다." 어차피 새로 만들 것(인증·결제)이 핵심이고, 살릴 것은 데이터/프롬프트뿐이다.

## 2. 의사결정

### 결정 1 — 서버리스 ❌ → 단일 백엔드 서버 ✅

결제·환불은 **트랜잭션·멱등성·상태 일관성·웹훅 수신**이 핵심이다. 서버리스 함수로 쪼개면 이 흐름이 파편화돼 오히려 관리가 어려워진다. 결제 콜백(토스페이먼츠 승인/취소 웹훅)을 안정적으로 받는 "항상 떠 있는 신뢰 가능한 서버"가 어울린다.

### 결정 2 — Kotlin + Spring Boot (Ktor ❌)

돈을 다루는 제품이라 **검증된 생태계·레퍼런스**가 결정적이다. Spring Security, 트랜잭션, 검증, 토스페이먼츠 연동 예제가 모두 Spring 기준으로 풍부하다. 1인 운영에서 "막혔을 때 빠져나올 자료가 많은 것"이 무게보다 중요하다. Ktor는 가볍지만 결제·시큐리티를 직접 짜야 해 돈 다루는 제품엔 리스크.

### 결정 3 — 마이그레이션 ❌ → 새 프로젝트 (clean rebuild) ✅

> **"마이그레이션을 하면 보통 이전 코드 수준에 갇혀버린다."**

기존 tRPC 구조를 점진 이식하면 옛 설계(어정쩡한 이중 인증, 결제 미고려 유저 모델)에 발목 잡힌다. 새 레포에서 깨끗하게 설계하고, 기존 코드는 **참조용 자산**으로만 본다.

- **이식(copy & adapt)**: Gemini 프롬프트 텍스트, 타로 78장 덱 데이터, 스프레드 정의, 캐릭터 rpPrompt
- **재설계(rebuild)**: 인증, 유저 모델(잔액/재화 포함), 결제·환불, API 계약
- **폐기(drop)**: tRPC, better-auth(Discord), Drizzle 스키마, 이중 로그인 구조

### tRPC를 버리는 비용

기존 앱/웹/토스가 누리던 end-to-end 타입세이프(tRPC)는 사라진다. 대신 **REST + OpenAPI 스펙 기반 타입 생성**으로 대체한다. 토스 앱은 어차피 `tossLogin` REST 호출 패턴이라 손실이 작다. (프론트 타입 동기화는 OpenAPI codegen으로 보완 — 로드맵 참조)

## 3. 타깃 아키텍처

```
┌─────────────────────────────────────────────┐
│  클라이언트 (기존 t3-turbo 모노레포 재활용)     │
│  - apps/toss   (앱인토스 / Granite)  ← 1순위   │
│  - apps/expo   (앱)                            │
│  - apps/nextjs (웹)                            │
│         │ REST (OpenAPI codegen 타입)          │
└─────────┼──────────────────────────────────────┘
          ▼
┌─────────────────────────────────────────────┐
│  Spring Boot + Kotlin 백엔드 (신규 레포)        │
│                                               │
│  ├─ auth       토스 로그인 → JWT 발급/검증      │
│  ├─ user       유저·잔액(재화) 관리             │
│  ├─ reading    타로 리딩 (Gemini 호출)          │
│  ├─ fortune    일일 운세 (하루 1개 제약)         │
│  ├─ payment    토스페이먼츠 결제/환불/웹훅       │
│  └─ ledger     재화 충전·차감 트랜잭션           │
│                                               │
│  - Spring Security (JWT)                       │
│  - Spring Data JPA / Exposed                   │
│  - 토스페이먼츠 SDK 연동                         │
│  - Gemini API 클라이언트 (프롬프트 이식)         │
└─────────┬──────────────────────────────────────┘
          ▼
┌─────────────────────────────────────────────┐
│  Neon (서버리스 Postgres, 매니지드)             │
└─────────────────────────────────────────────┘

호스팅: Railway / Fly.io (매니지드, cold-start 없는 상시 가동)
```

### 기술 스택 (제안)

| 레이어 | 선택 | 비고 |
|--------|------|------|
| 언어/프레임워크 | Kotlin + Spring Boot 3.x | |
| 빌드 | Gradle (Kotlin DSL) | |
| 인증 | Spring Security + JWT | 토스 로그인 → 자체 JWT |
| DB 접근 | Spring Data JPA 또는 Exposed | JPA = 레퍼런스 多 / Exposed = 코틀린 네이티브. 1차는 **JPA 권장** |
| DB | **Neon** (서버리스 Postgres) | 깔끔한 새 시작 — 부가기능 없이 순수 Postgres, 브랜칭으로 개발/테스트 DB 분리 |
| 결제 | 토스페이먼츠 | 앱인토스 궁합 |
| LLM | Gemini (기존 프롬프트 이식) | |
| 호스팅 | Railway / Fly.io | 상시 가동, 매니지드 |
| API 문서 | springdoc-openapi | 프론트 codegen 소스 |

> **결제/재화 모델 (확정 — 충전형 재화)**: 유저가 재화(코인)를 **충전**하고, 리딩/운세 소비 시 **차감**한다. `payment`(토스페이먼츠 충전 결제·환불)와 `ledger`(재화 충전/차감 트랜잭션 원장)를 분리 설계한다. 잔액은 ledger 합산으로 도출(또는 유저 잔액 캐시 + ledger 정합 검증).

## 6. 원가 & 가격 책정

> 충전형 재화(코인) 모델의 코인 단가를 정하기 위한 **변동 원가 분석**. 핵심 변동비는 **Gemini API**. (호스팅은 월 고정비라 건당으론 0에 수렴, 토스페이먼츠 수수료는 충전액의 ~2-3%)

### LLM 단가 (Gemini 3.1 Pro Preview, 2026-06 기준)

| | 단가 (≤200k 토큰) |
|---|---|
| 입력 | $2.00 / 1M 토큰 |
| 출력 | $12.00 / 1M 토큰 (**thinking 토큰 포함**) |

- 출력이 입력의 **6배** 비싸고, **thinking(추론) 토큰이 출력에 합산**된다 → Pro 모델은 추론이 많아 **출력 길이·thinking이 비용을 지배**한다.
- 입력 토큰 줄이기보다 **출력 제어**가 비용 절감의 핵심.

### 건당 원가 추정 (환율 1,350원/$ 가정)

| 서비스 | 입력 토큰 | 출력+thinking | 건당 원가 |
|--------|-----------|---------------|-----------|
| 일일 운세 (카드 1장) | ~1,000 | ~2,300 | **~4원** (사실상 공짜) |
| 싱글 리딩 (1장) | ~2,000 | ~2,500 | **~46원** |
| 트리플 리딩 (3장) | ~3,000 | ~3,500 | **~65원** |
| 켈틱크로스 (10장) | ~6,000 | ~5,000 | **~97원** |

> **1회 리딩 원가 ≈ 50~100원.** 토스 수수료 ~3% 얹어도 코인 단가의 바닥은 100원 안쪽.

⚠️ **최대 불확실성 = thinking 토큰.** Pro의 추론량에 따라 출력 비용이 2~3배 튈 수 있다. **실제 호출 후 `usageMetadata`(실측 토큰)로 검증 필요** (상세 설계 전 1회 측정).

### 가격 책정 방향

- **일일 운세 = 무료** (원가 4원, 진입장벽 제거 → 유료 전환 깔때기 입구)
- **리딩 = 코인 차감, 스프레드 무게에 비례** (싱글 1코인 / 켈틱 더 많이 — 원가 비례)
- **코인 1개 ≈ 300~500원** 선이면 원가 대비 **5~10배 마진** (디지털 콘텐츠라 마진율 70~90% 가능)
- **충전 패키지**: 3,300 / 5,500 / 11,000원 계단 + 큰 패키지에 **보너스 코인**으로 큰 충전 유도, 중간 패키지 "추천" 앵커링
- 진짜 비용은 돈이 아니라 **사용자 획득** — 가격을 짜게 잡기보다 무료→유료 전환 깔때기 설계가 매출을 좌우

> 구체적 충전 패키지·코인 차감표는 상세 설계 단계에서 thinking 토큰 실측 후 확정.
