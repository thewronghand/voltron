# 새 훅 추가 시 설계 지침

훅(`.claude/settings.json`의 `hooks` 또는 `*-workflow/hooks/*.sh`)을 추가할 때 따른다.

## 훅 이벤트 카탈로그

| 이벤트 | 트리거 시점 | 비용 | 권장 용도 |
|--------|------------|------|----------|
| `SessionStart` | 새 대화 시작 (1회) | 낮음 | 컨텍스트 주입 |
| `SessionEnd` | 대화 종료 시 (1회) | 낮음 | 작업 로그 백업 — IDE에서는 잘 안 끝나니 효과 제한적 |
| `PreCompact` | 자동 압축 직전 | 낮음 | 핵심 결정 백업, 트랜스크립트 보존 |
| `UserPromptSubmit` | 사용자 메시지 제출 직후 | 매번 | 매 턴 컨텍스트 주입. 너무 많으면 어텐션 분산 |
| `PreToolUse` | 도구 호출 직전 | 매번 | 차단·교정 (보호 브랜치 가드 등) |
| `PostToolUse` | 도구 호출 직후 | 매번 | 후처리 (prettier), 자가 교정 피드백 주입 |
| `Stop` | Claude 응답 종료 시 | 자주 | 알림, 가벼운 검증. 무거운 작업 금지 |

## 설계 원칙

### 1. 차단보다 교정 (Verbose Failure)

훅이 `exit 2`로 차단할 때, stderr에 **재시도용 구체 명령**을 같이 보낸다.

나쁨:
```bash
echo "develop 직접 편집 금지" >&2
exit 2
```

좋음:
```bash
echo "develop 브랜치 직접 편집은 금지됩니다." >&2
echo "다음 명령으로 피처 브랜치를 만든 뒤 재시도하세요:" >&2
echo "  git stash" >&2
echo "  git checkout -b feat/<설명> origin/develop" >&2
echo "  git stash pop" >&2
exit 2
```

차이: Claude가 stderr를 읽고 자가 교정 가능. 사용자 개입 없이 흐름 이어짐.

### 2. Silent Success / Verbose Failure

검증 훅은 **통과 시 침묵, 실패 시 자세히** 말한다.

- 통과 시 stdout 없음 → 컨텍스트 노이즈 0
- 실패 시 어디서·왜·어떻게 고치는지 명시

### 3. 가볍게

훅은 매 도구 호출마다 실행될 수 있다. **2초 이상 걸리는 훅은 만들지 말 것**. 무거운 검증(npm test, 풀 빌드)은 사용자 명시 호출로 옮긴다.

### 4. 선택적 우회 가능하게

가드형 훅은 환경변수로 일회성 우회 가능하게 만든다. (예: `ALLOW_DIRECT_DEVELOP=1`)

이유: 정말 가끔 필요한 예외 상황에서 훅을 끄려고 settings.json 수정하는 건 위험하다. 1회성 우회 경로를 명시적으로 두는 게 안전.

### 5. 한 훅 = 한 책임

훅 하나가 여러 일을 하면 디버깅이 어려워진다. 컨벤션 검사·포매팅·타입체크는 각자 분리.

## 추가 전 자가 점검

1. **이 훅이 막을 실수가 실제로 발생했나?** (lessons 또는 메모리에서 확인)
2. **수동으로 처리해도 될 만큼 드문 일은 아닌가?** (1년에 한 번 발생하는 일을 위해 매 도구 호출마다 훅 도는 건 비용)
3. **훅 없이 가이드 문서만으로 충분하지 않나?** (강제 필요한 것만 훅으로)
4. **훅이 실패할 때 사용자가 멈출 것인가, Claude가 자가 교정할 것인가?** 후자가 되도록 설계

## 추가 후 관찰

- 첫 1주: 훅이 트리거되는지, 노이즈는 없는지 확인
- 첫 1개월: 훅이 막은 실수가 있었는지 lessons에 기록
- 3개월 후: 트리거 빈도 검토. 너무 안 트리거되면 회수, 너무 자주 트리거되면 메시지 개선
