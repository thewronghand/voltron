# 새 에이전트/스킬 추가 시 기준

에이전트(`.claude/agents/*.md`)와 슬래시 커맨드/스킬(`.claude/commands/*.md`)을 추가할 때 따른다.

## 에이전트 vs 스킬 vs 가이드 — 어떤 걸 만들어야 하나

| 도구 | 정체 | 적합한 경우 |
|------|------|------------|
| **에이전트** | 격리된 컨텍스트에서 도는 전문가 | 메인 컨텍스트에 결과만 돌려주면 되는 작업. 많은 파일 탐색·외부 검색·리뷰 등 |
| **슬래시 커맨드/스킬** | 사용자가 명시 호출하는 정형 절차 | 매번 같은 단계로 진행되는 작업. 사용자 컨펌이 중간에 들어가도 OK |
| **가이드 문서** | Claude가 작업 중 참조하는 규칙 | 매 작업마다 다르게 적용되는 판단 기준 |

## 새 에이전트 추가 기준

추가 전 다음 질문에 답할 수 있어야 한다:

1. **기존 에이전트로 안 되는 게 뭔가?**
   - 새 도메인 (예: 백엔드 추적은 bro, 프론트 구조는 architect)
   - 새 도구 권한 (예: 외부 웹 접근은 researcher)
   - 다른 책임 (예: read-only 분석 vs 코드 수정)
   - 답이 모호하면 → 추가 보류, 기존 에이전트 프롬프트 보강이 우선

2. **메인 컨텍스트에 위임할 만큼 무거운 작업인가?**
   - 파일 5개 이하 읽고 끝나는 작업 → 메인이 직접
   - 10개 이상, 또는 외부 검색·DB 조회 등 컨텍스트 부피 큰 작업 → 에이전트 위임

3. **에이전트가 받아야 할 입력·돌려줄 출력이 명확한가?**
   - 입력 모호 → 메인이 매번 프롬프트를 새로 짜야 함 → 에이전트의 가치 반감
   - 출력 형식 정해두기 (예: reviewer는 Critical/High/Medium/Low 분류)

4. **이 에이전트가 자주 호출될 것인가?**
   - 1년에 몇 번만 호출될 거면 추가하지 않음. 호출당 컨텍스트 비용·유지보수 비용 > 가치

## 새 스킬/슬래시 커맨드 추가 기준

1. **이 절차가 정형화돼 있나?**
   - 매번 같은 단계 → 스킬 적합
   - 매번 다른 판단이 들어감 → 가이드 문서가 적합

2. **단계가 멱등한가?**
   - 같은 명령 두 번 실행해도 안전 (이미 끝난 단계 자동 스킵)
   - 멱등하지 않으면 디버깅·재실행 시 위험

3. **사용자 컨펌 지점이 명확한가?**
   - 자동 진행할 부분과 사용자 결정 받을 부분 분리
   - 자동 진행이 너무 길면 사용자가 흐름을 못 따라감 — 중간 게이트 추가

4. **실패 시 어떻게 되나?**
   - 부분 실패 시 처음부터 다시 vs 중단 지점부터 재개 — 명시
   - 중단 조건 카탈로그화 (예: 머지 충돌 → 중단, 빌드 트리거 실패 → 중단)

## 위치

- 프로젝트 전용: 해당 프로젝트의 `.claude/agents/*.md` 또는 `commands/*.md`
- 전역: `~/.claude/skills/*` (다른 프로젝트에서도 사용)

## 형식 (에이전트)

frontmatter에 `name`, `description`, `model`, `tools` 명시:

```markdown
---
name: agent-name
description: >
  한 줄 설명 — 언제 호출해야 하는지가 명확해야 함.
  메인 컨텍스트가 패턴 매칭으로 위임 결정.
model: opus
tools: Read, Grep, Glob, Bash
---

## Role
구체적 책임 한 줄

## What You Do
- 항목별로 무엇을 하는지

## What You Don't Do
- 명시적 비책임 (read-only인지, 파일 수정 가능한지)

## Output Format
어떻게 결과를 메인에 돌려줄지
```

## 추가 후 관찰

- 첫 사용 시 메인 컨텍스트가 잘 위임하는지 확인
- 위임 안 하고 메인이 직접 처리하면 → description이 모호함 → 보강
- 결과가 메인에 너무 길게 돌아오면 → output format 압축 지시 추가
