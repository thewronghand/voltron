# 하네스 운영 — 유지보수 측면

규칙·훅·에이전트를 잘 추가하는 것 외에, 시간이 지나면서 발생하는 운영 이슈들.

## 1. 설정 파일 검증 (Config Lint)

`.claude/`, `*-workflow/` 안의 설정·가이드 파일도 코드처럼 깨질 수 있다. 흔한 깨짐:

- **고아 참조 (orphan reference)**: 가이드 A가 가이드 B를 링크하는데 B가 삭제·이름 변경됨
- **죽은 cross-ref**: lessons에서 "X 패턴은 Y 컴포넌트로 해결" 했는데 Y가 더 이상 존재 안 함
- **빈 description**: 에이전트/스킬의 frontmatter `description`이 비어있어 위임 결정 못 함
- **포맷 불일치**: 같은 종류 문서인데 헤딩 레벨·표 형식이 들쑥날쑥

검증 시점:
- workflow에 큰 변경 들어가는 PR 머지 직전
- 새 가이드 추가 후
- 분기 점검 (3개월에 한 번)

수동 검증으로 충분. 자동화는 workflow가 더 커지면 도입 검토.

## 2. 도구 중립성 — AGENTS.md 표준 인지

2025년 9월 [AGENTS.md](https://agents.md/) 오픈 포맷이 발표되면서 OpenAI Codex, Google Jules, Cursor, Zed 등이 같은 형식을 지원하기 시작했다.

**현 상황**: 개인 프로젝트들은 Claude Code 단일 도구 사용 중. CLAUDE.md 형식 그대로 유지.

**미래 대비**: 만약 다른 코딩 에이전트(Cursor, Copilot, Codex 등)를 병행 사용하게 되면:
- `AGENTS.md`로 단일 진실 소스 마이그레이션 검토
- CLAUDE.md는 AGENTS.md를 symlink하거나 include하는 방식
- 도구별 특수 규칙은 별도 부속 파일 (`AGENTS.claude.md` 등) 패턴 가능

**지금 당장**: 마이그레이션 비추. 단일 도구 환경에 최적화됨. 도구 추가 시점에 재검토.

## 3. 분기 점검 체크리스트

3개월에 한 번 (혹은 큰 작업 사이 텀이 생길 때) 다음을 점검:

### CLAUDE.md (전역 + voltron + 프로젝트)
- [ ] 모든 규칙이 최근 6개월 내 한 번 이상 작동했나?
- [ ] 작동 안 한 규칙은 회수 또는 가이드로 이동
- [ ] 새 규칙이 기존 규칙과 중복되지 않는지
- [ ] Critical Rules가 한 화면 안에 보이는지
- [ ] voltron CLAUDE.md와 프로젝트 CLAUDE.md 간 중복 없는지

### 가이드 (`guides/`)
- [ ] 각 가이드가 누구에게 언제 참조되는지 명확한지
- [ ] 가이드 A → B → C로 링크 따라가다 끊긴 곳 없는지
- [ ] 외부 링크(URL) 살아있는지

### 메모리 + lessons
- [ ] 메모리 인덱스가 stale 안 됐는지 (200줄 후반은 잘림)
- [ ] lessons 중 더 이상 적용되지 않는 게 있는지 (아키텍처 변경 등으로)
- [ ] 같은 종류 메모리가 중복돼 있지 않은지

### 에이전트 + 스킬
- [ ] 사용 빈도 0인 에이전트/스킬 있나?
- [ ] 새 에이전트 description이 위임 결정에 충분한지

### 훅
- [ ] 각 훅이 막은 실수가 실제로 lessons에 기록돼 있나?
- [ ] 트리거 빈도 너무 낮은 훅 (= 가상 위험 대비)
- [ ] 트리거 빈도 너무 높은 훅 (= 노이즈 가능성)

## 4. 변경 기록

하네스 자체에 큰 변경(에이전트 추가, 새 가이드, 큰 리팩토링)이 있을 때 어디 기록할지:

- 작은 변경(규칙 추가/수정): git commit 메시지로 충분
- 중간 변경(새 가이드, 새 훅): why-tho에 짧게 기록
- 큰 변경(아키텍처 재편, 도구 교체): bootstrap/ 안에 changelog 또는 별도 문서

규칙: **하네스 변경도 프로젝트 작업처럼 다룬다.** 커밋·문서화·필요시 lessons.

## 5. 회수의 윤리

규칙·훅·에이전트를 회수(삭제)할 때 다음을 남긴다:

- **언제 추가됐는지**: git log로 추적
- **왜 회수하는지**: commit 메시지에 명시 ("3개월간 트리거 0회", "아키텍처 변경으로 무관해짐" 등)
- **회수 결정의 근거**: principles 어느 항목에 따른 결정인지

이게 있으면 미래에 비슷한 패턴 다시 추가하려 할 때 "전에 빼봤더니 별일 없었음"을 기억할 수 있다.
