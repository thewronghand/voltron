# r2: r1 리뷰 지적 반영

r1 작업(같은 브랜치, 미커밋)에 대한 독립 리뷰에서 나온 지적이다. 아래만 고친다. 범위·금지 사항은 r1 지시와 같다.

## 고칠 것
1. **확인 창 테스트 빈틈** — `SongDetail`(SongEditor)의 곡 삭제와 `LyricsEditor`의 저장된 가사 지우기에 화면 컴포넌트 수준 테스트를 더한다(`tests/confirmation.test.tsx`의 SongList 케이스 패턴). 최소: 취소·ESC → `deleteSong`/가사 지우기 API 호출 없음, 확인 → 정확히 한 번 호출, 확인 창이 떠 있는 동안 숨김(visible false)·작업 시작(active)·탭 전환·가사 변경 등 기존 취소 effect가 다루는 조건이 생기면 창이 닫히고 호출 없음. 각 가드(`removeRequest || active || !visible`, `!visible || clearRequest`, 취소 effect)를 하나씩 지우면 실패하는지 변이로 확인. TimingEditor의 `!visible`·`choosing` 가드도 같은 방식으로 테스트가 잡게 한다.
2. **`useConfirm`의 `waiting` 가드 테스트** — 두 번째 `confirm()`이 즉시 `false`로 끝나고, 첫 번째 Promise는 이후 취소/확인으로 정상 종료(남지 않음)되는지 검증. `waiting` 가드를 지우면 실패해야 한다. SongList `removeTarget` 가드가 `waiting`과 중복이면 KISS 기준으로 정리 여부를 판단해 보고.
3. **확인 창 위 파일 드롭** — Modal은 포털이지만 React 합성 이벤트가 React 트리로 버블링돼, 확인 창(백드롭 포함) 위에 파일을 드롭하면 `App.tsx`의 `<main onDrop>`이 실행되어 곡 추가 Modal이 확인 창 위에 겹쳐 열린다. 확인 창이 열려 있을 때 드롭(및 dragover)이 바깥으로 전달되지 않게 한다(예: `useConfirm`이 반환하는 `dialog`를 감싸는 요소에서 drop/dragover 전파 차단 — 더 단순하고 맞는 방법이 있으면 그것으로). 테스트로 고정.
4. **진행 막대 통일** — `ProgressBar.tsx`에서 결정형(라이브러리 `Progress`)과 불확정 막대의 높이·색이 다르다(값 null↔숫자 전환 시 높이 2px 튐, 색 바뀜). 불확정 막대를 라이브러리 Progress와 같은 높이·트랙/채움 색(라이브러리 토큰 클래스, 예: `bg-bg-subtle`/`bg-primary` — d.ts·dist에서 실제 클래스 확인)으로 맞춘다. 반대로 Progress를 앱 색으로 덮어쓰지 않는다.
5. **Checkbox.Line className 반복** — 같은 `peer-focus-visible…` 클래스 문자열이 6~7번 반복된다. 한 곳(상수 또는 작은 래퍼)으로 모은다.
6. **Stepper 오버라이드·테스트 결합** — `LyricsEditor.tsx`의 `[&_.truncate]:whitespace-normal`처럼 라이브러리 내부 클래스명에 기대는 오버라이드가 꼭 필요한지 다시 보고, 필요 없으면 제거, 필요하면 이유 주석. `tests/uiMigration.test.tsx`가 라이브러리 내부 고정 문자열("진행 단계")에 묶인 부분은 앱이 보장하는 것(바깥 그룹 이름 "가사 편집 단계", 현재 단계 aria-current, "(건너뜀)")만 검증하게 정리.

## 고치지 않을 것 (보고에만 남김)
- 확인 창 첫 포커스가 헤더 닫기(X)라 Enter=취소, 본문이 aria-describedby로 연결 안 됨 — 라이브러리 Modal 한계. 앱에서 억지로 우회하지 않는다.
- Checkbox가 label 안에 div를 렌더하는 것, Radio.Item 카드 모양 — 라이브러리 쪽.
