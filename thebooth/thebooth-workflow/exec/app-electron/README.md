## 메인이 실측으로 찾은 것
- 백그라운드 Electron 창은 macOS 창 캡처(computer-use)가 갱신되지 않거나 실패한다. 화면은 바뀌었는데(접근성 트리에는 "다시 시작" 버튼이 있음) 이미지는 이전 그대로. → 화면 검증은 Playwright `_electron`으로 실제 앱을 띄워 조작·캡처한다(`e2e/`).
- 사이드카 Python을 SIGKILL → 앱이 "예기치 않게 종료" + "다시 시작" 표시, 다시 시작 시 새 포트로 ready. 개발 앱 종료 후 uv·Python 프로세스 잔존 없음.
- r2 리뷰 MEDIUM(구독마다 화면 되감김)은 서버 코드로 사실 확인: 새 연결은 Last-Event-ID 없이 커서 0부터 보관 이벤트를 재생했다. 클라이언트 우회로는 판정 근거가 없어 사이드카 계약을 바꿨다(스냅샷에 순번 id, 이후 이벤트만). 커서를 0으로 되돌리는 변이에서 SSE 테스트 3개가 실패함을 확인.
- r2의 "받은 양"은 사이드카 안내 문구를 정규식으로 잘라 만든 추정치였다 → 제거. manifest 모델은 사실상 파일 하나(htdemucs 둘째 파일은 21바이트 yaml)라 퍼센트만으로 충분.
- r3 실행에서: 단계 표시 순서가 실제(`write`가 `align`·`render`보다 먼저)와 달라 "영상 만들기 진행 중" 아래 "저장 완료", 가이드를 새로 추출해도 "음표 캐시: 미사용", 보조 버튼(secondary filled)이 비활성처럼 보임, 같은 이름 버튼("파일 선택")이 여럿, 취소 문구 중복, "스텀" 오타 → r4.

- r5에서 Codex가 "정렬 캐시 적중 시 두 번째 write"를 write 진행 이벤트 개수(3번째)로 추론 → 계약에 없는 `jobs.py` 내부 동작(단계 전환 시 마무리 이벤트, write에 advance 없음)에 결합. 리뷰 MEDIUM으로 확인 후 사이드카가 단계를 일관되게 보고하도록 바꾸고(r6) 추론을 지웠다. 교훈: 화면이 서버 상태를 추론하기 시작하면 서버 보고를 고치는 편이 단순하다.
- r6 전후 폭탄마 MR·ASS·MP4 바이트 동일(결과물 불변).
- r6의 "단계 전환 시 message 비우기"가 기본 렌더 경로의 "가사 영상 렌더 중..."을 지웠다(안내가 `write` 단계에서 나간 뒤 `video.render`가 `render`로 진입). 주입 렌더러만 쓰는 테스트라 못 잡음 → 안내를 단계 진입 뒤로 옮기고 두 경로를 다 도는 테스트 추가. 수정을 되돌린 변이에서 실패 확인. 실제 앱 렌더 중 안내 표시 확인, 결과물 바이트 동일.
- CLI 동작 변화: `thebooth video`도 "가사 영상 렌더 중..." 한 줄을 출력한다(이전엔 `make`만).

## 실제 앱 확인 (Playwright `_electron`, 개발 서버 렌더러)
- 파일 대화상자만 main 프로세스에서 대체하고 나머지는 화면 조작. 스크립트 `e2e/`, 스크린샷 `screens/`.
- 준비: 실제 모델 폴더(전부 설치됨) 표시 / 빈 HOME에서 받기 → 진행 → 취소("취소됨"·"다시 받기") → 다시 받기 → 설치됨.
- 만들기(완료 기준): 폭탄마 전곡, 가라오케 모드 + 멜로디 가이드 + 가사 영상(가사·보조 파일, ja) → MR·MP4·ASS 생성, 결과 화면·Finder 버튼. 분리·음표·정렬 캐시가 모두 적중해 10초.
- 캐시 없는 실행: 30초 클립 htdemucs+가이드 끝까지 / 40초 클립 가라오케 분리 중(11%) 취소 → "취소했습니다".

## 후속
- 패키징(2b): `file://` 렌더러 출처(null) 문제 → 커스텀 프로토콜, 사이드카 실행 경로, uv 동봉.
- Windows 실기 미검증(프로세스 트리 종료 `taskkill /T /F` 포함).
- SSE 스냅샷·순번 원자성은 잠금 범위로 보장(코드 검토). 경쟁 자체를 결정적으로 재현하는 테스트는 없음.
