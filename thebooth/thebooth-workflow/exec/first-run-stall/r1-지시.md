# 작업: thebooth — 첫 실행 환경 구성(uv sync) 다운로드가 멈췄을 때 알아차리고 다시 시도할 수 있게

레포 `thebooth-code`(이 폴더), 브랜치 `feat/first-run-stall`(main 기준, 이미 만들어 둠).

## 필독
- `../CLAUDE.md`(TS `any` 금지, 폴더 밖 import는 `@/`, 화면 문구 한국어)
- `../thebooth-workflow/planning/00-기획.md` 결정 기록 "2b 패키징·첫 실행 환경 구성 구현 결정"(진행은 단계+경과 시간+로그, uv 출력에서 퍼센트를 만들지 않는다 — 화면이 문구를 추측하면 깨진다)

## 증상 (메인 실측, 패키징 .app, 빈 임시 HOME)
첫 실행 구성에서 실행 환경용 Python(약 66MB)은 받았지만, 이후 `uv sync`가 **약 15분 동안 진행이 전혀 없었다**: uv 캐시가 76KB에서 그대로, venv 60KB, uv 프로세스 CPU 0%, PyPI 파일 서버(Fastly)와 TCP 연결 하나가 ESTABLISHED인 채 데이터 없음. 같은 시각 `curl https://pypi.org/simple/...`은 0.85초. 첫 시도는 10분 넘게 멈춘 걸 메인이 강제로 끝냈고, 다시 시도한 실행은 약 15분 정지 뒤 갑자기 1분 안에 약 800MB를 받아 끝났다(곡 목록까지 1058초). 그동안 준비 화면은 '설치 중'과 경과 시간만 보여 사용자는 멈춘 건지 알 수 없다.

## 해야 할 일
1. **정지 감지**: 설치 단계에서 진행 신호가 일정 시간(예: 3분) 없으면 상태에 "진행이 멈춘 것 같다"는 표시를 더한다. 진행 신호는 uv 출력 줄 **또는** uv 캐시·venv 폴더 크기 증가(주기적으로 재기 — 비용이 큰 재귀 크기 계산은 피하고, 예를 들어 캐시 폴더의 다운로드 임시 파일 크기나 파일 개수 변화 등 가벼운 신호를 판단해 고른다). 진행이 다시 생기면 표시를 지운다. 화면이 uv 문구를 해석하지 않는다(위 결정).
2. **화면**: 준비 화면에 한국어 안내 — 예: "몇 분째 진행이 없습니다. 네트워크 상태를 확인하거나 '취소 후 다시 시도'를 눌러 보세요." + 버튼('취소 후 다시 시도' = 기존 취소 → 재시도 흐름을 한 번에). 이미 받은 패키지는 uv 캐시에 남으므로 재시도가 처음부터 다시 받지 않는다는 점을 한 줄로.
3. **uv 네트워크 설정**: 멈춘 연결이 끝없이 매달리지 않도록 uv의 HTTP 시간 제한·재시도 환경변수(`UV_HTTP_TIMEOUT` 등 — 동봉한 uv 0.13.7 문서·`uv --help`로 실제 이름과 기본값 확인)를 명시적으로 넘길지 판단하고, 넘긴다면 값과 근거를 보고. 상태 기록(`runtime/state.json`)의 "동기화 명령 해시"가 바뀌어 기존 사용자에게 재동기화를 일으키는지 확인하고, 일으킨다면 피하거나(해시 대상에서 제외 등) 근거를 보고.
4. **테스트**: 정지 감지(가짜 시계·가짜 진행 신호로 결정적으로), 진행 재개 시 해제, 취소 후 다시 시도, 화면 문구. 수정 전 코드에서 정지 감지 테스트가 실패하는지 확인.
