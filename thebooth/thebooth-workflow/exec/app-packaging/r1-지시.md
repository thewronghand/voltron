## 요구사항

### 1. 이름 (사용자 결정)
- OS가 다루는 이름은 전부 ASCII `thebooth`: electron-builder `productName`·`appId`(`com.thewronghand.thebooth`)·실행 파일·`.app` 파일·설치 폴더·산출물 파일 이름. Electron `app.name`·창 제목·`index.html` `<title>`·macOS 메뉴·정보 창도 `thebooth`.
- 부제 `난이제TJ가내가원하는노래를넣어주길기다리지않겠어왜냐면내길은내힘으로찾아가는거니까`는 **README와 앱 화면에만** 쓴다.
  - 앱 화면: `App.tsx` 헤더의 작은 글씨 "더부스" 자리(`<p className="text-xs ...">`)를 이 부제로 바꾼다. 아래 큰 제목 "나만의 노래방 연습"은 그대로. 긴 한 단어라 좁은 창(최소 너비 720px)에서 넘치지 않게 줄바꿈 처리(`break-all` 등)한다.
  - README 첫 제목 아래에 부제 한 줄.
- 화면에 남은 "더부스" 표기가 있으면 위 규칙에 맞게 정리(사람이 보는 앱 이름은 `thebooth`).

### 2. 사용자 데이터 폴더 통일
- Electron 기본 userData는 앱 이름을 따라간다. **`app.whenReady()` 전에** Electron의 userData를 Python platformdirs와 같은 뿌리 아래 하위 폴더로 고정한다.
  - Python `paths.data_dir()` = platformdirs `user_data_path("thebooth", appauthor=False)` → macOS `~/Library/Application Support/thebooth`, Windows `%LOCALAPPDATA%\thebooth`(Electron `appData`는 Windows에서 Roaming이라 다르다 — 주의).
  - Electron userData = `<그 뿌리>/electron`. 경로 계산은 `electron` import 없는 순수 함수로 두고 단위 테스트(darwin·win32 각각, 환경변수 주입).
  - 개발 모드도 같은 규칙(개발·앱 공유가 원칙). 이 값은 r2에서 가상환경 위치(`<뿌리>/runtime/...`) 계산에도 쓸 것이니 재사용 가능한 모듈로.

### 3. 패키징 앱의 화면 출처 (커스텀 프로토콜)
- `file://`는 Origin이 `null`이라 사이드카 CORS(`*`·`null` 금지)에 막힌다. 표준·보안 커스텀 스킴으로 고정 출처를 만든다: `app://thebooth` (스킴 이름은 바꿔도 되나 이유를 보고).
  - `protocol.registerSchemesAsPrivileged`(ready 전) + `protocol.handle`로 `out/renderer/` 아래 파일만 제공. 경로 탈출(`..`, 인코딩된 `%2e%2e`, 역슬래시, 절대 경로) 차단, 다른 호스트 거부, 없는 파일 404. 판단 로직은 `electron` import 없는 순수 함수로 두고 단위 테스트.
  - 패키징 모드 `rendererUrl` = `app://thebooth/index.html`. 기존 `rendererOrigin()`은 http/https만 받으니 `app:` 출처를 받도록 확장(그 외 스킴·null은 여전히 거부). `assertRenderer`의 출처 검사도 그대로 통과해야 한다.
  - 사이드카에 `THEBOOTH_ALLOWED_ORIGINS=app://thebooth`가 넘어가야 한다. **Python `allowed_origins()`와 Starlette CORS가 `app://thebooth` 출처에서 실제로 preflight·요청·SSE를 통과하는지 pytest로 확인**(필요하면 서버 쪽 최소 수정). Chromium이 이 스킴에서 실제로 보내는 `Origin` 헤더 값은 r2 실기에서 확인하니, 추정이면 보고에 "추정"이라고 적는다.
- CSP: 프로덕션 `index.html` 메타 CSP가 `app://thebooth`에서 스크립트·스타일·폰트·이미지를 막지 않고, `connect-src`는 `http://127.0.0.1:*`만(사이드카). 개발 모드 CSP(`developmentCsp`)는 유지.
- 패키징 모드에서도 `will-navigate` 차단·`setWindowOpenHandler` deny·권한 거부는 그대로.

### 4. 사이드카 실행 경로 분리 (구조만)
- 지금 `SidecarManager`는 `spawn('uv', ['run','thebooth','serve','--port','0'], {cwd})`로 고정돼 있다. 실행 명령(`command`·`args`·`cwd`·추가 env)을 바깥에서 주입받는 형태로 바꾼다(예: `launch: { command, args, cwd, env }`). 개발 모드 동작·테스트(실제 `uv run` 통합 테스트 포함)는 그대로 통과해야 한다.
- 패키징 모드에서는 이번 라운드에 사이드카를 띄우지 않는다. 화면이 "처리 엔진을 시작할 수 없음"류로 멈춰도 괜찮지만 **앱이 죽거나 빈 화면이면 안 된다**. 상태 메시지는 "실행 환경 구성은 아직 지원하지 않습니다" 정도의 한국어 한 줄(r2에서 교체).

### 5. 패키징 도구
- **electron-builder**(devDependency, 버전 고정)로 설정 파일 `app/electron-builder.yml`(또는 `.config.*`).
  - macOS: arm64, 대상 `dmg`(+ 검증용으로 `.app`이 남는 `dir` 산출이 자연히 생기면 그대로). 서명·공증 없음(`identity: null`), 하드닝 런타임 끔. 아이콘은 기본값 그대로 둬도 됨.
  - Windows: x64, 대상 `nsis`(사용자 단위 설치, `perMachine: false`). 이 맥에서 크로스 빌드. **wine이 없어서 nsis가 막히면** `zip` 대상으로 바꾸고 이유를 보고(rcedit 등).
  - 산출물 이름 `thebooth-${version}-${os}-${arch}.${ext}`, 출력 폴더 `app/dist/`(이미 .gitignore).
  - `extraResources`로 다음을 앱 리소스에 넣는다(r2에서 쓴다):
    - `python/`: 레포 루트의 `pyproject.toml`, `uv.lock`, `README.md`(pyproject `readme` 필드가 참조 — 빌드에 필요), `src/thebooth/**`(`__pycache__` 제외). 테스트·`.venv`·캐시는 넣지 않는다.
    - `uv/`: 대상 플랫폼의 `uv` 실행 파일(macOS `uv`, Windows `uv.exe`). `uvx`·`uvw`는 빼도 된다.
  - asar는 써도 된다(렌더러 프로토콜 핸들러가 asar 안 파일을 읽을 수 있게 — `app.getAppPath()` 기준). `extraResources`는 asar 밖 `process.resourcesPath`.
- **uv 동봉**: 빌드 때 받는 스크립트 `app/scripts/fetch-uv.mjs`(Node 내장 모듈만). 버전·sha256 고정:
  - uv **0.13.7**
  - `https://github.com/astral-sh/uv/releases/download/0.13.7/uv-aarch64-apple-darwin.tar.gz` sha256 `81b811b57e4624df7ed3aac148e0359100d9962f3d9dce00aec533dc2e086731`
  - `https://github.com/astral-sh/uv/releases/download/0.13.7/uv-x86_64-pc-windows-msvc.zip` sha256 `0cdc5b38fe5a8168ed6a25814f5ba43c21d313dd3187314fccb37b7cec46e021`
  - 받은 압축 파일 sha256 불일치면 실패(종료 코드 ≠ 0). 이미 받은 게 맞으면 재다운로드 안 함. 저장 위치는 `app/build/uv/<플랫폼>/`처럼 레포 안이되 **.gitignore에 추가**. 압축 해제는 macOS 기본 `tar`(bsdtar는 zip도 푼다).
  - 패키징 스크립트: `pnpm dist:mac`(arm64 dmg), `pnpm dist:win`(x64) — 각각 fetch-uv(해당 플랫폼) → `electron-vite build` → electron-builder.
- `electron-builder`가 pnpm 의존성을 제대로 담는지 확인(`node_modules` 링크 문제 시 `.npmrc`나 `pnpm-workspace.yaml` 설정으로 해결하고 보고).

### 6. Windows ffmpeg manifest 항목 (사용자 승인, 값은 메인이 실측)
- `src/thebooth/manifest.json`에 `ffmpeg-windows-x64` 추가. 기존 `ffmpeg-macos-arm64` 항목 형식 그대로:
  - `platform`: `win32-x86_64` (`models.current_platform()` 값 형식)
  - `description`: `libass·libx264가 포함된 Windows x64 FFmpeg`
  - `license`: `GPLv3 빌드 (FFmpeg 9.0.2 + libass·libx264, gyan.dev essentials 빌드) — 남에게 배포 시 소스 제공 의무`
  - 파일 `ffmpeg.zip`: url `https://github.com/GyanD/codexffmpeg/releases/download/9.0.2/ffmpeg-9.0.2-essentials_build.zip`, size `114768076`, sha256 `60f467265b1e312373dbcd92200c2618a74850f98d3d078e94296bb3fa2047ba`, extract `ffmpeg.exe` sha256 `3256173f3f8bffd7df12227c68adf68025edb1832273a9530688a7bb1ed8edec` (zip 안 경로 `ffmpeg-9.0.2-essentials_build/bin/ffmpeg.exe` — 기존 압축 해제는 파일 이름으로 하나를 찾는다).
- `THEBOOTH_FFMPEG`는 덮어쓰기용으로 남긴다. Windows에서 미설치 시 안내가 `models pull ffmpeg-windows-x64`로 바뀌어야 한다. 기존 테스트 중 "win32면 THEBOOTH_FFMPEG 안내"를 기대하는 것은 새 동작에 맞게 고치고, "manifest에 없는 플랫폼이면 THEBOOTH_FFMPEG 안내"는 다른 가짜 플랫폼으로 유지.
- 앱 준비 화면이 플랫폼에 맞는 ffmpeg 하나만 보여주는지 확인(이미 `supported`로 거르고 있으면 그대로).
- README의 Windows ffmpeg 안내·모델 표를 새 동작에 맞게 고친다.
