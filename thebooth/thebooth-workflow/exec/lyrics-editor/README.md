## 사용자 결정
- 화면 구성안(곡 상세 탭 "만들기·내보내기 / 가사", 가사 탭 3단계 붙여넣기 → 루비 확인 → 타이밍)과 선택지 다섯 개 권장안 승인: 탭 배치, 발음 줄은 일본어 타이밍 자동 추종, 보컬 파형 표시, 텍스트가 같은 블록의 타이밍 수정은 재정렬 후에도 유지, 곡 설정 Modal의 가사 파일 칸은 가사 탭으로 이동(CLI는 그대로).
- 구현은 메인이 직접(사용량 사정) → 주간 사용량 초기화 후 r2부터 다시 Codex(사용자 지시).
- 루비 처리는 옵트인(기본 꺼짐) — 루비 확인이 곡당 100곳 넘게 나와서. 일본어도 가사만 붙이면 한 줄 한 블록.

## 메인이 실측한 것
- **루비 추정 규칙 교체.** Codex 초안(한자 뒤 가나를 거의 통째로 루비로 잡고 끝 글자가 오쿠리가나 같으면 하나 뺌)은 폭탄마 45블록 중 정답(루비 없는 가사 파일)과 일치 0블록, 묶음 정답률 47.8%, 111묶음 전부 '확인 필요'.
  - 정답이 있는 두 곡(폭탄마, 다른 곡 하나 — 205묶음)으로 측정: 루비 없는 묶음 94개, 루비 길이/한자 수는 2.0·1.0·1.5가 대부분, 가나 전체가 루비인 경우는 7%.
  - 블록마다 (발음 음절 − 가나 음절(っ·ん·ー·작은 가나 제외))가 0 근처면 루비 없는 한자 0개(73블록 중 45개 전부), 양수면 루비 없는 한자 한 글자당 약 1.5~2음절.
  - 새 규칙: 남는 음절을 루비 없는 묶음들의 읽기 추정(한자 1.7음절)으로 채우는 조합을 고르고(16묶음 이하 전수, 넘으면 근사), 루비 길이는 한자 수×1.5 반올림. **묶음 정답률 74.1%, 루비 유무 95.1%, '확실'로 표시했는데 틀린 경우 0.** 루비/오쿠리가나 경계는 사전 없이 판별할 수 없어(정답 유무를 알아도 경계 규칙은 약 60%) 확인 필요 표시는 여전히 많다(205 중 155).
  - 평가 스크립트는 가사 내용을 출력하지 않고 수치만 낸다(스크래치에 두고 레포에 넣지 않음).
- 실제 앱(`e2e/lyrics.mjs`, 1단계 launch 재사용): 곡 추가·만들기(캐시 3초) → 가사 탭에 폭탄마 나무위키 원문 붙여넣기 → 45블록·섹션 10개·각주 1개 제거 → 루비 확인 111곳(경계 토글 1회로 110곳, 블록별 '추정 확인'으로 0곳) → 저장하고 정렬(Whisper 39초) → 수정 전 MP4 내보내기 → 타이밍 탭에서 2번째 글자 시작 경계를 → 키 두 번(100ms) 이동·저장('수정됨') → 수정 후 내보내기 → **ASS 150줄 중 첫 블록의 일본어·발음 2줄만 달라짐**(발음 줄이 일본어 타이밍을 따라감).
  - 이 E2E는 추정을 고치지 않고 일괄 확인했으므로 일부 블록 원문이 틀린 채로 정렬됐다(동작 확인용). 가사가 보이는 화면은 스크래치에만 저장.
  - 타임라인 파형이 곡 전체 1,200칸 요약이라 블록(수 초)에서는 세로선 30개 남짓 → 최대치 10,000칸으로 올림.
- CLI `make` 기본 경로(수정본 없음) 결과 바이트 main과 동일.
- 리뷰 HIGH(같은 텍스트 블록 [A,B,C,A]에서 앞 A를 지우면 수정본이 뒤 A로 옮겨 붙음)를 리뷰어 재현 스크립트로 확인 → 수정 후 `modified=False`. 회귀 테스트 2개는 수정을 되돌리면 실패.
- 파형·재생 WAV 계산은 전역 잠금 안에 유지(리뷰 MEDIUM 보류): 잠금 밖에서 스템을 열면 Windows에서 만들기 작업의 스템 교체(`os.replace`)가 실패할 수 있다(1단계 목록 조회 MEDIUM과 같은 이유). 첫 계산 뒤에는 곡 폴더 캐시.
- 수정 후 실제 앱 E2E 재통과(정렬 35초, 타이밍 수정 후 내보내기 ASS 2줄만 변경), 파형이 블록 안에서 촘촘하게 보임, CLI 기본 경로 바이트 동일.
- 남은 것: 프로세스 강제 종료 시 가사 저장 저널 복구 경로 테스트, 리뷰 LOW(맞닿은 경계 버튼 두 번 Tab, 경계 버튼 현재 시각 미노출, 루비 버튼 이름에 가나 없음, tablist 방향키, 숨은 타이밍 탭의 오래된 rows 등), Windows 실기, 반주기 재생.
- 재리뷰 LOW 보류: 곡 상세의 '수정된 블록 수'가 범위 밖이라 무시된 수정본까지 셀 수 있음, 같은 가사로 재정렬해 1초 넘게 바뀌면 수정본이 안내 없이 적용되지 않음, 0초 글자가 수십 개 이어지는 극단 경우의 정규화.
- 갱신 간헐 문제: 2회 멈춘 실행 모두 서버 기준 분리·음표·정렬 'ready'(곡 폴더에 alignment.json)인데 화면 '다음 · 타이밍'이 꺼진 채. r2 뒤 실제 앱 E2E 3회 연속 통과(정렬 217·96·79초, 다른 세션 CPU 부하), r3 뒤 1회 통과(214초). 어느 경합이 34분 멈춤의 실제 원인이었는지는 당시 로그가 없어 단정 못 함.
- 남은 LOW: SSE가 running인데 서버엔 작업 없음일 때 진행 표시와 열린 입력이 같이 보임, 서버 종료 보고 시 SSE 오류 문구 잔존 가능, 자동 판별에서 텍스트를 비웠다 다시 붙이면 루비 꺼짐, 사이드카 테스트 하나가 부하에서 10초 응답 제한에 걸려 한 번 실패(재실행 통과).
