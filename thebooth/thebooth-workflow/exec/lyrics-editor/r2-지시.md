# 작업: thebooth — 만들기 작업이 끝났는데 곡 상세(가사 탭)가 갱신되지 않는 간헐적 문제

레포 `thebooth-code`(이 폴더), 브랜치 `feat/lyrics-languages`(미커밋 변경 있음 — 가사 루비 옵트인·한국어/영어 한 줄 한 블록. 그대로 두고 그 위에서 작업).

## 필독
- `../CLAUDE.md`(TS `any` 금지, 폴더 밖 import는 `@/`, 화면 문구 한국어)
- 앱: `app/src/renderer/src/features/songs/SongDetail.tsx`(SongEditor의 `currentJobId`·`useJob(jobId, onUpdate)`·`completed` ref·`refresh`), `features/songs/LyricsEditor.tsx`(`timingReady = song.status.alignment === 'ready' && !dirty`, '다음 · 타이밍' 버튼), `features/songs/songLogic.ts`(`currentJobId`), `hooks/useJob.ts`, `lib/jobStream.ts`, `lib/jobEvents.ts`
- 사이드카 SSE 계약: `README.md` "앱과의 계약"(첫 이벤트는 스냅샷, 이후 순번 이벤트)

## 증상 (메인 실측)
실제 Electron 앱 E2E(`../thebooth-workflow/exec/lyrics-editor/e2e/lyrics.mjs`)에서 3번 중 2번:
가사 탭에서 '저장하고 정렬' → 만들기(정렬) 작업 시작 → 작업이 서버에서 끝남(곡 폴더에 `alignment.json` 생성, 서버 `Library.list()` 기준 분리·음표·정렬 모두 `ready`) → 그런데 화면의 '다음 · 타이밍' 버튼이 켜지지 않고 34분 넘게 그대로. 사이드카·Python CPU는 0%(작업 끝남). 같은 흐름이 통과한 실행에서는 정렬이 177초 걸렸고, 멈춘 실행 중 하나는 30~40초 걸렸다(작업이 빨리 끝날수록 의심). 1단계부터 있던 경합일 가능성이 있다.

## 해야 할 일
1. **원인을 코드로 특정**하고 보고한다. 의심 지점(확인할 것): 구독 전에 작업이 이미 끝나 터미널 이벤트가 구독 콜백으로 오지 않는 경우(`useJob`의 `onUpdate`가 구독 콜백에서만 불림), `jobId`가 `song.job` → `requested` → `last_job` 사이에서 바뀌며 재구독할 때 터미널 상태를 놓치는 경우, `completed` ref 비교, `start()` 안의 `refresh()`와 SSE 터미널 처리 순서, `LyricsEditor`의 `dirty`(저장 직후 `savedSignature`와 현재 본문 불일치), 숨은 탭에 마운트된 컴포넌트.
2. **고친다**: 터미널 상태를 놓치지 않게(예: 구독 콜백이 아니라 상태 값 변화로 완료 처리 — 이미 터미널인 스냅샷을 받은 경우도 한 번 갱신), 그리고 **안전망**: 곡에 진행 중 작업(`song.job`)이 있는 동안 SSE와 무관하게 일정 간격(예: 5초)으로 곡을 다시 읽어 서버 상태와 맞춘다(작업이 끝나면 멈춤, 컴포넌트가 사라지면 정리). 화면이 서버 상태를 추론하지 않게 한다(2a 교훈: 서버 보고를 그대로 쓴다).
3. **회귀 테스트**(vitest, 결정적으로): 구독 시점에 이미 끝난 작업, 재구독 중 터미널 이벤트, 저장 직후 dirty 계산 — 각각 수정 전 코드에서 실패하는지 확인하고 보고(변이 확인).
