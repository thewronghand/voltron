# r3: 2차 리뷰 지적 반영

r2 이후 호출 세션은 코드를 고치지 않았다. 실곡 MR·ASS·MP4 바이트 동일을 다시 확인했다.

## 1. ffmpeg가 사이드카 stdin을 물려받지 않게 (video.py·tools.py)
- 문제: `serve`의 stdin은 앱과 연결된 파이프이고 EOF 감시 스레드가 읽는다. ffmpeg가 같은 stdin을 상속하면 키 입력 처리로 바이트를 가로챌 수 있다(`q`면 정상 종료 → 잘린 MP4가 성공으로 끝남).
- 정책: 모든 ffmpeg 호출에 `stdin=subprocess.DEVNULL`을 주고, 렌더 명령에 `-nostdin`을 넣는다. 출력 바이트에는 영향이 없어야 한다.
- 자식 프로세스 환경에서 `THEBOOTH_TOKEN`을 뺀다(필터한 env 전달).
- 테스트: Popen 인자에 `stdin=DEVNULL`·`-nostdin`이 있는지, env에 토큰이 없는지. Windows `CREATE_NO_WINDOW` 전달도 `os.name` monkeypatch와 `subprocess.CREATE_NO_WINDOW`(raising=False)로 확인한다.

## 2. 비싼 계산 결과를 취소 전에 캐시 (pitch.py·align.py·pipeline.py)
- 문제: 분리는 캐시 저장 후 취소를 확인하는데, 음높이 추출·정렬은 계산 직후 추출기 안에서 `check_cancelled`를 불러 결과를 버린다. 몇 분짜리 Whisper 정렬이 취소 한 번에 사라진다.
- 정책: 추출기·정렬기 **안의 계산 후 취소 확인을 지운다**. `pipeline`에서 결과를 캐시에 저장한 **다음** 취소를 확인한다. 정렬은 실패 기준 검증을 통과한 결과만 저장한다는 기존 규칙을 유지한다.
- 테스트: 음표·정렬 계산 직후 취소돼도 캐시가 남고, 다음 실행에서 적중하는지.

## 3. CLI 출력 복원 — 모델 받기 (progress.py·cli.py)
- 이전 동작: `thebooth models pull`의 "받는 중: …"과 `%` 진행 줄은 **stdout**이었다. r1부터 stderr로 바뀌었다.
- 정책: `models pull` 명령은 예전처럼 stdout에 쓴다. 진행 객체에 출력 스트림을 넘길 수 있게 하거나 pull 전용 콘솔 진행을 둔다. `make`의 진행 출력은 지금처럼 stderr다.
- 테스트: CLI pull의 stdout에 받는 중·진행 줄이 있는지.

## 4. 중복 검사 제거 (server.py·pipeline.py)
- 서버가 큐에 넣기 전에 만든 `PreparedMake`를 버리고, 작업 실행 때 `validate_make`를 다시 돈다(가사 두 번 로드, `check_ass` 두 번 실행).
- 정책: 서버는 준비 결과를 작업에 넘겨 `pipeline.make(prepared=...)`가 재사용하게 한다. 단 **실행 직전에 모델·ffmpeg가 아직 설치돼 있는지만 가볍게 다시 확인**한다(큐 대기 중 삭제 대비, 파일 존재·크기 수준). 이유를 주석으로 남긴다.

## 5. 실패해도 부분 결과 보고 (jobs.py·pipeline.py)
- MP3·ASS(+백업)를 쓴 뒤 렌더가 실패하면, 실패 이벤트·스냅샷에도 `partial`(쓴 파일, `ass_backup`)을 담는다. 취소와 같은 형식이다.
- 테스트를 추가한다.

## 6. 견고성·문서
- `watch_parent`: `sys.stdin`이 None이거나 `fileno()`가 실패하면(`AttributeError` 포함) traceback 없이 stderr에 "부모 감시 비활성" 경고 한 줄만 쓰고 계속한다. 테스트를 둔다.
- 완료된 작업 기록 정리: 끝난 작업이 100개를 넘으면 오래된 것부터 지운다(대기·실행 중인 작업은 지우지 않는다). 지운 작업의 SSE·조회는 404다. 테스트를 둔다.
- README "앱과의 계약"에 다음을 적는다.
  - 서버는 분리 캐시가 있어도 분리 모델 설치를 요구한다(이유 포함). 그래서 앱은 `pull`이 끝난 뒤 `make`를 보내야 한다.
  - SSE는 화면에 보이는 작업당 하나만 연다(연결 하나가 스레드를 쓰기 때문).
  - stdin에 아무것도 쓰지 않는다(EOF만 의미가 있다).
